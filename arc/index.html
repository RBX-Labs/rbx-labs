AI Reliability Commons (ARC)

AI can sound right and still be wrong. ARC helps teams see what happened, check the evidence, pause risky actions, and turn failures into fixes they can test. It gives AI workflows a simple reliability loop: find the failure, capture the evidence, choose a safe next step, test the fix, and improve the workflow.

Why ARC exists

Make the failure useful after it happens.

AI systems can produce plausible answers while hiding missing evidence, conflicting sources, or unverified actions. ARC turns that failure into a record a maintainer can inspect, test, and repair.

Failure→Evidence→Fixture→Safe Outcome→Test→Repair

The operational difference

Plausible is not the same as trustworthy.

Prompt-only run
“Yes, Feature X is compatible with the 4.2 migration. You can proceed.”
  • No source record
  • No conflict visible
  • No proof of compatibility

approved · unsupported

Runtime-aware run
“I can’t confirm 4.2 compatibility yet. The sources conflict; run the adapter fixture and attach the result.”
  • Coverage, freshness, and conflict recorded
  • Read-only authority held
  • Runtime escalation is not presented as human approval
  • No human rationale is invented while review is pending
  • No action or independently observed effect is invented

needs maintainer review · inspectable

Adopt it in an afternoon

Start with one workflow and one failure.

  1. 1 Choose one workflow action and define its authority boundary.
  2. 2 Record observable evidence, including freshness and conflicts.
  3. 3 Keep runtime outcome, human disposition, rationale, acknowledgement, and observed effect separate.
  4. 4 Define when the system should proceed, abstain, escalate, and verify the result.
  5. 5 Turn the next meaningful failure into a fixture and regression test.
