Why ARC exists

Make the failure useful after it happens.

A plausible answer is not proof. ARC turns a silent failure into evidence, a reproducible fixture, an expected safe outcome, and a repair that another project can inspect.

Failure→evidence→fixture→safe outcome→test→repair

The operational difference

Plausible is not the same as trustworthy.

Prompt-only run
“Yes, Feature X is compatible with the 4.2 migration. You can proceed.”
  • No source record
  • No conflict visible
  • No proof of compatibility

approved · unsupported

Runtime-aware run
“I can’t confirm 4.2 compatibility yet. The sources conflict; run the adapter fixture and attach the result.”
  • Coverage, freshness, and conflict recorded
  • Read-only authority held
  • Runtime escalation is not presented as human approval
  • No human rationale is invented while review is pending
  • No action or independently observed effect is invented

needs maintainer review · inspectable

Adopt it in an afternoon

Start from the action, not from the prompt.

  1. 1 Bound the authority the workflow actually needs.
  2. 2 Record observable evidence signals and their limits.
  3. 3 Separate runtime outcome, human disposition, accountable rationale, execution acknowledgement, and observed effect.
  4. 4 Define abstain, escalate, and post-action verification paths.
  5. 5 Turn the next meaningful miss into a fixture and regression test.
